# Codex 同聊天模型同步入口

本分支增加可选的 App Server 控制代理。在新用户轮次进入 Codex 前完成路由，将真实模型和推理档位交给 Codex；HTTP 网关执行同一份已绑定计划。切回原生时恢复用户选择的原生模型，不需要把所有模型统一限制到最小窗口。

## 启用与恢复

1. 启动本分支的 qpool 控制台，启用已配置的路由。在 Codex 中保留真实模型选择，例如 Sol。
2. 在 **Agent 接入** 中接入常驻入口，再点击 **生成模型同步入口**。
3. 保存页面显示的启动命令，退出 ChatGPT/Codex 桌面后运行。启动器会拒绝在已有桌面运行时强行启动或终止它。
4. 打开原来的 OpenAI 聊天。在控制台切换 **使用原生 / 使用 qpool**；当前回复保持原模型，下一次正常提问使用新模式。
5. 之后通过生成的入口启动桌面。直接从原应用图标启动不会加载控制代理，仍受旧 HTTP 入口的模型能力兼容检查约束。

启动器只为它启动的应用设置 `CODEX_CLI_PATH`，没有修改系统环境或替换应用二进制。首次连接控制代理需重新启动桌面；聊天内切换无需重新启动。

彻底恢复时，在控制台选择 **彻底断开**，退出桌面后从原应用图标启动。原配置沿用现有备份恢复规则。恢复后即使继续使用生成的包装器，它也直接执行原生 Codex。

## 行为与边界

- Codex 原生提供方保持 `openai`，原聊天 ID 和模型可见历史保持不变。
- `turn/start` 的模型、推理档位及 Plan 模式中的对应设置一起更新。权限、审批、工具执行和事件流仍由 Codex 管理；审批模型保持原生账号。
- 路由只计算一次，生成不含提示词的持久化计划。HTTP 请求须匹配计划的聊天、登录身份、实际模型、轮次及路由版本；失败不会自动跨账号重放。
- 切到小窗口模型前，Codex 如先用旧模型压缩，则保留旧执行账号和模式完成压缩，再使用新模型生成。该压缩可能丢失历史细节；没有统一降低原生模型窗口。
- 原生模型与推理档位偏好独立保存。qpool 的自动模型选择不会覆盖切回原生时应恢复的偏好。
- 路由分类只接收有界的最近文本视图，长文本会截断并标记不完整；实际发给 Codex 的输入和完整模型历史不经过这项截断。
- 新排队消息由控制代理持久保存在权限为 `0600` 的 `control-inputs.db`，支持编辑、删除和重排。上一轮结束后才预选模型，因此等待期间切换模式会作用于下一条消息。输入不会再交给原生自动队列绕过预选。
- 排队提交前持久标记在途状态；断连或超时等结果未知时保留输入并停止后续自动提交，避免重复执行。确认聊天实际结果后，可显式删除该待确认项；删除不等于取消已经开始的回复。准备失败的消息保留在队列里，可编辑或手动重试。
- 原生已有的未发送队列不自动导入或删除；检测到原生队列或活动轮次时，新托管队列等待其处理结束。启用入口或彻底断开前应先处理待发送消息。彻底断开不会删除私有队列；再次通过控制入口恢复聊天时继续处理，原生入口不会读取该私有队列。
- 模型栏与实际模型同步：先调用原生设置更新，再开始轮次；桌面在 `turn/started` 时会写回提交前的旧模型，代理随后重发最近一条原生设置通知纠正显示。这不重写原生权限，也不把路由模型保存为用户的原生模型偏好。
- 本轮未启用用户主桌面入口。隔离桌面的真实显示由用户确认，协议调用、实际模型与进程由测试交叉核实。多代理内部自行创建的新聊天不包含在本轮真实验收中。

## 2026-11-08 验证报告

环境：macOS，安装版 Codex `0.167.0-alpha.3.2`，现有订阅登录的隔离副本，真实 `gpt-6.1-sol` 与 `gpt-6-astra`。测试未使用付费 API；此次模型切换保持同一个订阅账号，跨账号迁移不是本次真实测试的结论。

### 1. 双向切换与工具调用：通过

分别以原生和 qpool 创建聊天，执行原生 → qpool → 原生、qpool → 原生 → qpool，累计 9 个轮次。每个聊天的控制代理进程保持不变，聊天 ID 保持不变，历史文件标记均正确回忆。首次轮次实际调用读取文件工具。Codex 的 `thread/read.model` 与请求记录的实际执行模型一致，验证使用与桌面一致的 `features.code_mode_host=true`。

### 2. 旧聊天升级与跨窗口压缩：通过

先经旧 `/legacy/v1` 入口创建持久聊天并实际读文件，再一次性加载控制代理，恢复原聊天。升级后 3 轮使用同一进程和聊天：Sol 原生 → Astra qpool → Sol 原生。

为了以有限额度触发边界，仅在隔离目录将 Astra 的模型目录窗口设为 32k，并注入测试填充。真实 Codex 在切换时产生两次 `contextCompaction`：先由原生 Sol 处理旧历史，随后 Astra 处理新窗口并回答。压缩后及切回 Sol 后均能回忆原标记。这证明缩小窗口的压缩路径，不能据此推导已经压测了完整 272k/500k 极限。

### 3. 自动化回归与独立审查

最终代码全仓 276 项回归通过（143.220 秒），覆盖旧入口、原生偏好、路由/轮次绑定、旧执行身份、启动参数、持久队列 CRUD、身份隔离、提交防重、未知结果不越序、在途状态空窗、准备期间变忙、无效参数保护和通知顺序。独立复审发现的三项问题均已修复并补回归：排队准备期间变忙不得变成当前轮追问、无效 CRUD 不得误改队首、自动失败使用合法的无轮次 `warning` 通知。复审无新增可复现问题。`git diff --check` 通过；前轮 JavaScript 检查证据仍适用，本轮未改前端脚本。

### 4. 桌面启动弹窗：修复并通过

隔离桌面首次启动显示“无法加载组织设置”。根因为控制包装器把 `app-server --print-startup-config` 当成持续 JSON-RPC 会话；桌面调用该命令时关闭 stdin，代理因 EOF 提前终止原生进程，导致启动配置输出为空。原生同一调用能返回有效 JSON，因此本次弹窗不是组织权限错误。

修复后一次性启动检查及 App Server 子命令直接交给原生执行，并跳过选项值再识别命令，避免名为 `proxy` 的文件误触发透传。关闭 stdin 的真实调用中，启动配置和 `app-server help` 的 stdout、退出码均与原生一致。独立审查及参数分类回归通过。用户确认隔离桌面正常进入聊天界面、弹窗消失。

### 5. 桌面模型栏同步：修复并通过

修复前真实请求已切换，但界面仍显示 Sol。先增加原生设置通知后，GUI 复验仍失败；读取本机桌面代码后确认它在 `turn/started` 时从提交前的乐观状态恢复旧名称。最终在该事件后重发引擎已经确认的设置通知，用户再次实际操作确认通过。

| 模式 | 回执中的实际模型 | 用户观察的模型栏 | 原历史标记 |
| --- | --- | --- | --- |
| qpool | gpt-6-astra | GPT 6 Astra | 一致 |
| 原生 | gpt-6.1-sol | GPT 6.1 Sol（用户确认成功） | 一致 |

两轮均为同一已保存聊天，桌面 PID 89730、控制代理 PID 89939、引擎 PID 89940 未变。界面操作由用户完成，不能称为全自动 UI 测试。通知重放仅使用原生完整设置；独立测试确认新用户设置在事件前后到达时，最终都保留新设置。

### 6. 自动排队与等待期间切换：修复并通过

原先“队列列表为空、start 返回 not found”并非消息丢失：当前原生版本会在 `queue/add` 后内部自动取走并开始执行，绕过控制代理。旧测试助手还会在等待 RPC 结果时丢弃通知，掩盖了 `turn/started`。本轮修正测试助手，分离响应与通知，并改为验证自动执行。

真实模型验证了 9 轮双向切换，其中 qpool 轮次通过托管队列自动开始。另在上一轮真实工具执行期间排入三条消息，编辑一条、重排、删除一条，再由原生切到 qpool：上一轮保持 Sol，两条剩余消息按重排后的顺序各自成为独立 Astra 轮次，修改内容生效，删除项未执行，旧标记正确。队列最终为空，没有重启进程。

最终组合复验同时覆盖旧聊天升级、32k 跨窗口压缩、排队自动开始、忙碌期间多条排队和模式切换。一次准备旧聊天的请求遇到上游 HTTP 500，原生重试后完成，但严格回执断言判该次失败；保留失败证据后重新执行，不删除失败记录或放宽完成状态断言。另一次组合测试因固定 HTTP 请求数假设拒绝了正常的重复压缩；依据实际 `contextCompaction` 事件，改为核对独立轮次、顺序、原生/qpool 模型边界及全部请求完成状态，最终新跑的组合场景通过。

脱敏的真实验证结果见 [control-routing-live-20261108.json](artifacts/control-routing-live-20261108.json)。原配置及原登录文件的哈希保持不变，测试副本中的登录凭证已删除。

